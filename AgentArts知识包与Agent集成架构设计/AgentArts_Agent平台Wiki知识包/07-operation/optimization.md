## 1. 平台优化能力总览

0916 把优化正式划分为**四条路径、两个层次**：

| 功能 | 层次 | 定位 | 说明 |
| --- | --- | --- | --- |
| **轨迹分析** | 诊断 | 问题诊断入口 | 针对 Agent Skill 执行逻辑迭代优化前的**归因诊断**；分析 Agent 历史 Trace 发现问题，根因下探到 Session ID 与 Span ID 级 |
| **工具优化** | 配置层 | 工具描述迭代 | 针对工具的**描述文案、调用前置校验规则、接口使用限制**做针对性优化，修复工具匹配错误、参数填写异常 |
| **Skill 优化** | 配置层 | Skill 文档迭代 | 针对 Agent **Skill 的执行逻辑**迭代优化，修复逻辑漏洞与描述缺陷，改善工具调用准确性 |
| **模型优化（+ 模型部署）** | 模型层 | 端到端定向训练 | 基于**强化学习**对 Agent 中的大模型端到端定向训练，突破提示词工程的准确率上限，以小尺寸模型实现大尺寸模型在专属场景的高精度表现 |

### 1.1 两条操作路径

**路径一：诊断 → 配置层优化（轨迹分析 / 工具优化 / Skill 优化）**

- **运行逻辑**：通过分析 Agent 历史 Trace 发现问题，针对工具描述和 Skill 文档进行自动化优化。轨迹分析作为路径起点负责诊断归因，采样 Trace 数据分析（失效分析、意图分析、执行摘要），并将根因精准下探定位至具体 **Session ID 与 Span ID 级别**（如定位到某 Span 调用工具时缺失必填参数）。工具优化与 Skill 优化作为执行层，**既可由轨迹分析通过"智能优化"自动执行，也可独立手动创建**。
- **优化结果即时生效，无需训练模型。**
- **适合场景**：工具调用频繁失败（参数缺漏、选错工具）；Agent 任务流程跑偏、规避调用工具或过早终止；尚不清楚表现不佳的根因需要先做诊断。

**路径二：模型训练与部署 → 模型层优化**

- **运行逻辑**：通过在线强化学习算法对模型参数端到端定向训练。**将待训小模型置换入真实 Agent 环境中试错交互**，由用户设定的评判规则对强化学习算法生成的多组回答进行对比打分与参数更新，从**模型权重层面**根治幻觉与格式缺陷，并阶段性保存"模型快照"，随后可选择合适模型部署至 Agent。
- **适合场景**：受限于推理成本或响应速度无法使用更大尺寸模型，希望训练让小模型在特定场景达到大模型效果；确认问题根因**在模型推理能力本身**（格式输出不稳定、逻辑推理跑偏、意图分类不准确、幻觉频发）。

## 2. 轨迹分析（诊断入口）

### 2.1 失效分析

对 Agent 会话进行**根因归因**，识别导致 Agent 输出不正确或任务未完成的原因。系统自动将失效会话归类为若干**故障类别**（如"智能体决策与推理失效"、"工具执行失败"），并针对每类故障归纳具体根本原因，精确定位到受影响的**会话与执行步骤（Span）级别**。

### 2.2 支持的优化对象

| 类型 | 说明 | Trace 数据来源 |
| --- | --- | --- |
| 单智能体 | 平台低代码创建的单智能体应用 | 平台**自动采集并上报**，无需配置 |
| 智能体运行时 | 高代码本地开发、托管至 AgentArts 运行时的智能体 | 部署至运行时后自动上报（工具优化/Skill 优化支持） |
| 第三方托管 | 平台外开发运行、通过观测 OpenAPI 上报 Trace 的智能体 | 手动对接观测功能后上报 |

> ⚠️ **两个关键限制**：
> 1. **轨迹分析仅支持"单智能体"与"第三方托管"**（不含运行时/高代码）；而**工具优化与 Skill 优化支持"智能体运行时"**。设计优化闭环时要按目标能力选择智能体形态。
> 2. **单智能体当前仅支持采集通过 API 调用产生的 Trace，暂不支持控制台预览调试产生的数据。**

### 2.3 任务配置

| 项 | 说明 |
| --- | --- |
| 分析方向 | 当前支持"失效分析" |
| 优化对象 | 单智能体 / 第三方托管 |
| **委托** | 必须选择已创建的 **IAM 信任委托**授权平台访问该 Agent 的 Trace 数据。创建要求：委托名称自定义、**信任主体类型选"云服务"**、**云服务填"智果 Agent 优化"**、其他默认；创建后授权项选 **`AgentArtsRLAnalysisTaskAgencyPolicy`** |
| 执行方式 | **单次执行**（设时间范围，适合临时诊断）/ **重复执行**（周期性自动运行，适合持续监控） |
| 筛选条件 | 可按特定属性过滤目标 Trace，缩小到关注的会话子集（如特定用户群/业务流程） |
| 数据采样 | 采样比例、采样数据上限；数据量少时可适当提高比例 |
| 标签 | 键值对，用于任务自定义标记与分类管理 |

### 2.4 结果解读

失效分析结果以**故障类别列表**呈现，每行为一个故障类别；单击"详情"展开该故障类别的完整诊断报告。

支持**一键智能优化**：由轨迹分析根据失效分析诊断结果自动创建工具优化 / Skill 优化任务，全程无需人工配置。

## 3. 工具优化（配置层）

### 3.1 问题模型

**工具（Tool）** 是 Agent 可执行的最小动作单元——**不限于插件或 MCP**，任何 Agent 可调用的外部能力（查询订单状态、搜索网页、调用计算接口、发送消息通知等）都属工具范畴。

**根因认知（核心洞察）**：模型调用工具时**完全依赖工具的文本信息**做决策（选哪个工具、传什么参数、何时调用）。若文本信息有问题，调用行为就会出错。**这类问题的根因不在模型本身，而在工具说明写得不够好。** 工具优化**全程不改动模型**，仅优化工具配置信息。

| 问题类型 | 典型表现 |
| --- | --- |
| **工具匹配错误** | 模型在功能相近的工具之间混淆选择，如把"查询订单状态"误用为"查询物流信息" |
| **接口释义模糊** | 工具描述对功能边界、适用条件说明不清晰，模型无法判断何时该使用 |
| **入参规范混乱** | 参数的类型、格式、取值范围、必填/选填等约束说明不完整，导致传入错误参数 |
| **调用规则不清** | 调用前提条件、依赖关系、频率限制未明确说明，导致调用错误 |

### 3.2 优化维度

系统根据 Trace 中的实际错误模式，自动判断需要优化哪些维度：

| 维度 | 说明 |
| --- | --- |
| **工具介绍文案** | 工具名称说明与功能描述：明确工具**做什么、不做什么、与其他工具的边界** |
| **调用前置校验规则** | 调用前需满足的前提条件，如"需先完成验证"或"需先调用工具 A 获取 ID" |
| **接口使用限制** | 调用频率限制、并发约束、数据量上限等运行约束说明 |

### 3.3 产出

平台自动从历史 Trace 与工具调用日志中提取数据，分析工具调用错误模式，**针对存在问题的工具生成优化后的描述文案信息**供使用。

> 与轨迹分析的关系：可手动创建，也可**由轨迹分析自动创建**（系统从 Trace 提取优化目标并启动任务）。

## 4. Skill 优化（配置层）

**触发条件**：确认 Agent 任务执行异常，且根因在于 **Skill 文档描述不够完整或准确**。

**机制**：平台自动从该 Agent 的历史执行轨迹中提取与所选 Skill 相关的数据，**批量分析执行过程中暴露的共性问题**，生成优化后的 Skill 文档，包括补充后的执行步骤、完善后的准入条件与边界处理逻辑。

**支持的优化对象**：智能体运行时 / 第三方托管（与工具优化一致）。

**产出**：优化后的 Skill 文档（供参考与使用）。

> Skill 的结构与加载机制见 [00-overview/managed_agents.md](../00-overview/managed_agents.md) 第 5 节。

## 5. 模型优化（模型层，强化学习）

### 5.1 定位与适用边界

**核心机制**：把一个小尺寸模型置入你的 Agent 运行环境，让模型针对你提供的业务问题**反复试错作答**，系统根据你定义的**奖励规则自动打分**——高分巩固、低分纠正，逐步让模型学会在专属场景下输出更精准的结果。

**优化范围**：当前可对**单智能体中的模型**、**工作流大模型节点 / 意图识别节点中的模型**进行定向调优。

**推荐使用场景**：

| 场景 | 痛点 | 模型优化效果 |
| --- | --- | --- |
| **严格格式输出与意图路由** | 意图识别节点偶尔输出多余解释性废话，导致下游 JSON 解析崩溃 | 强制模型按特定格式输出，仅输出如 `{"result": 10}` 这种极度干净、100% 符合正则的结构化数据 |
| **复杂逻辑推导与数学计算** | 倾向自行推算而非调用计算工具导致误差；不给出具体数值而返回表达式（如输出 `(a+b)/2`）；选择题不直接答选项 | 通过"思维链格式奖励"+"数值匹配奖励"，逼迫模型在给出最终答案前进行深度 `<think>` 思考，并确保数值与标准答案绝对等价（容忍 1.0 等于 1 的合理误差） |
| **精准工具调用** | 面对数量多且参数复杂的工具，模型常选错工具或填错必填参数 | 让小模型在特定工具集中反复试错练习，大幅提升专属业务环境下的工具调用准确率 |

**明确不推荐使用的场景**：

| 场景 | 原因 |
| --- | --- |
| 简单问答任务（基础知识检索、FAQ） | 优化提示词或接入 RAG 即可解决，无需动用模型优化资源 |
| 提升通用能力 | 模型优化旨在强化特定场景"单点能力"，**并非扩充通用知识或整体智能水平** |
| 训练数据极度匮乏 | 效果有限，且可能导致过拟合、泛化下降 |
| 问题边界模糊、输出标准难以量化（开放式创作、风格生成、情感陪伴） | 没有明确"标准答案"，**无法设计有效奖励函数**，强行使用会压缩表达多样性 |
| 样本分布极度不均衡 | 可能对高频样本过度拟合，低频但重要的边缘场景反而下降 |

### 5.2 优化对象配置要求（创建时平台会校验）

**单智能体**：
- 可包含 Prompt、知识库、插件、MCP 等能力，平台**在保留这些能力的前提下**对其中的模型做优化训练
- ❌ 智能体中**不能包含工作流**（或子工作流）
- ❌ 配置的**插件总数不能超过 5 个，MCP 总数不能超过 5 个**

**工作流**：
- ❌ 开始节点到被优化的大模型节点之间的路径上，**不能存在需要用户交互的节点**（如问答节点）。强化学习需模型在无人工干预下反复试错，用户交互节点会暂停等待输入，训练循环无法自动完成
- ❌ 若工作流存在循环结构，被优化的大模型节点**不能位于循环路径中**。循环会导致节点被反复执行，产生不可控的无限循环，消耗大量算力且无法收敛

### 5.3 基本原理（在线强化学习）

**强化学习三要素在 Agent 场景的映射**：

| RL 概念 | 在模型优化中对应 |
| --- | --- |
| 智能体 | 被训练的模型 |
| **环境** | 你在 AgentArts 中创建好的 **Agent 运行环境**（含预设 Prompt、知识库、插件、MCP 等） |
| **动作** | Agent 生成的回复文本、推理过程、工具选择、工具参数填写，以及单次任务中发起的多步工具调用过程 |
| **奖励** | 系统通过对比模型输出与标准答案，利用"奖励规则（正则/数值）"或"生成式裁判打分"给出分数 |

**三个阶段**：

1. **准备任务配置信息**：准备待优化 Agent 与训练数据，选择基础模型，设置奖励规则。数据集中 `input` 字段送入 Agent 环境触发模型作答（**此时 Agent 中的模型已被替换为被训模型**）；`reference_output` 作为裁判中心评分基准（规则裁判需精确匹配，大模型裁判做语义综合评分）。
2. **在线强化学习**（核心）：
   - **模型置换**：被训模型被直接置换到你的 Agent 中
   - **循环训练**：模型针对问题生成回答 → 裁判中心依据规则或大模型裁判打分 → 依据得分通过 **GRPO** 反向更新模型内部参数 → 进入"尝试作答 → 自动打分 → 自我进化"循环，高分巩固、低分纠正
   - **不直接拟合固定答案**，因此泛化能力更强
3. **部署与接入**：阶段性保存模型快照 → 挑选最优模型 → 部署 → 接入 Agent

### 5.4 优化方法：GRPO

平台预置 **GRPO（群组相对策略优化）** 算法。相比传统 RL（如 PPO）的工程优势：

| 优势 | 说明 |
| --- | --- |
| **去除庞大的评论模型** | 传统算法需同时运行两个大模型（生成模型 + 打分评论模型）；GRPO 通过数学设计彻底砍掉评论模型，训练轻量高效 |
| **群组对比优化** | 模型对同一道题**同时生成多个回答**，按奖励规则打分排序；得分最高的回答被强化，最低的被抑制，通过"组内对比"逐步学会输出更高质量回答 |

### 5.5 奖惩机制：三套打分标尺

| 机制 | 说明 | 适用 |
| --- | --- | --- |
| **规则奖励** | 用正则/数值规则精确匹配（`reference_output` 需精确匹配） | 格式严格、答案可精确判定的场景（意图分类、数学计算） |
| **生成式奖励** | 由**大模型作裁判**对输出做理解并打分，返回 **0.0–1.0 的绝对分数** | 开放式问答等无法用规则覆盖的场景 |
| **自定义奖励** | 编写一段 **Python 代码**在沙箱环境中执行计算奖励得分。**平台会把 Agent 运行的完整轨迹数据（Trajectory）传入代码**，而不只是最终回复文本 | 多步工具调用校验、轨迹合规性检查、组合评分逻辑、需第三方库（numpy/re 等）校验 |

**生成式奖励的评分标准撰写法则**（防止裁判"主观乱打分"）：

1. **确立核心评分原则与权重划分**：先说清最看重什么（正确性？语气？代码可执行性？）。示例："核心原则：正确性是基础（权重 90%），效率和清晰度是加分项（权重 10%）"
2. **精准量化分数段**：不能只写"根据质量打 0-1 分"，必须明确什么表现对应什么分数段。示例：1.0 分=完全正确、格式符合、无废话；0.7–0.9=正确但有轻微格式/语气问题；0.4–0.6=部分正确；0.0–0.3=错误或偏题
3. **设立"一票否决"的底线红线**：单独列出直接判 0 分的情况。示例："存在事实性错误、缺失关键信息、出现严重幻觉，直接记 0 分"

> ⚠️ 生成式奖励需填写"API 密钥凭证提供者"以获取评判模型调用权限；**裁判模型的 API 调用将产生费用**，由 MaaS 平台配置的 API Key 对应账户承担。

**自定义奖励的两项配置**：① 选择**代码解释器**作为沙箱运行环境（需提前创建并初始化，含安装 pip 依赖、上传自定义 Python 文件）；② 编写执行函数。

**权重提示**：同时配置"思维链格式奖励"与"正确性奖励"时，各项权重总和**无需严格等于 1**。为起辅助约束作用的思维链格式奖励设**较低权重（0.2~0.3）**，确保模型聚焦答案准确性，防止"投机取巧凑格式而答错题"。

## 6. 传统调优方法论（与平台能力互补）

平台优化覆盖了"配置层 + 模型层"的自动化路径，但 Prompt / RAG / 数据 / 评估器层面的问题仍需人工介入。以下方法论作为补充。

### 6.1 从现象到修复手段

| 现象 | 观测证据 | 典型根因 | 优化手段 | 回归验证 |
| --- | --- | --- | --- | --- |
| 端到端响应慢 | Root Span 耗时、最慢子 Span、模型平均耗时 | 工具/模型慢、冗余节点、重复生成 | 精简调用链、优化工具逻辑、调整模型、并行/缓存 | 耗时分位数、任务完成度不退化 |
| Token 成本飙升 | Tokens 总量、模型消耗 Top5、Model Span 输入 | 过长上下文、反复调高成本模型、无缓存 | 剪枝上下文、加判断与缓存、设频率/Token 阈值、分层选模型 | 单次 Token、成本、正确性和深度性 |
| 答案不符合预期 | Model Span Prompt/输出、工具输入/输出 | Prompt 含义不清、参数名不匹配、上下文拼接错 | 增强 Prompt 约束、统一参数语义、修复上下文组装 | 正确性、指令遵从、参数正确性 |
| RAG 幻觉 | Trace 中的问题、回答和检索 context | 知识缺失、检索不准、无证据仍生成 | 补文档、优化分段/召回/精排、加"无依据则拒答"规则 | 幻觉现象、引用相关性、真实准确 |
| **工具选错或参数错** | 工具 Span、轨迹、工具请求体 | 工具描述模糊、参数约束不清、调用时机不对 | **走平台「工具优化」任务**（不改模型，只改工具描述/前置校验/使用限制） | 工具选择质量、工具参数正确性、轨迹质量 |
| **Agent 流程跑偏 / 过早终止** | 轨迹、Span 序列 | Skill 执行逻辑缺陷、描述不全 | **走平台「Skill 优化」任务** | Skill 完整度、Skill 相关性、轨迹质量 |
| **格式输出不稳定 / 幻觉频发（根因在模型）** | 多轮同题输出漂移、格式校验失败率 | 模型推理能力不足，Prompt 已到上限 | **走平台「模型优化」**（GRPO 定向训练小模型） | 格式检查、正确性、任务完成度 |
| 安全/拒答边界失败 | 低分会话、对抗评测集、安全评估器 | 护栏缺失、红线样本不足 | 补拒答规则、护栏和合成对抗/红线样本 | 拒答检测、安全风险漏放、有害性、恶意性 |

> **选型口诀**：**描述问题 → 工具优化；文档问题 → Skill 优化；模型问题 → 模型优化；说不清 → 先做轨迹分析。**

### 6.2 BadCase 归因流程

1. **看整体**：用总体得分、雷达图、业务指标和评估器指标确定最薄弱维度
2. **抓 BadCase**：按低分、失败、高耗时、高 Token 或人工标注筛选具体样本
3. **反查 Trace**：使用回流保留的 `trace_id`，查 Root/Model/Tool Span 的输入、输出、元数据和日志
4. **先用平台诊断**：优先跑一次**轨迹分析**，让平台把根因下探到 Session/Span 级，再决定走哪条优化路径
5. **校准裁判**：人工检查评估器得分理由；对误判修正得分，对典型缺陷打标签
6. **分配责任面**：将问题归到 Prompt、Model、RAG、Tool/Gateway、Skill、工作流、数据或评估器本身
7. **单一变量修改**：一次只改一个主要因子，保留版本和实验说明，避免无法归因

### 6.3 评测集迭代策略

| 数据类型 | 来源 | 处理 | 用途 |
| --- | --- | --- | --- |
| 黄金样本 | 高分且人工复核的真实对话 | 校对为标准答案并发布版本 | 新版本上线门禁 |
| BadCase | 低分、失败、高延迟、人工投诉 | 保留 `trace_id`，按根因标签 | 专项修复和回归 |
| 边界/对抗样本 | 人工设计 + AI 合成 | 复核安全性与多样性 | 能力边界和护栏测试 |
| 生产分布样本 | Trace 随机/分层抽样 | 按场景、用户和流量比例保持分布 | 防止只优化少量典型问题 |
| **模型优化数据集** | 从智能体 Trace 回流 / 手动创建 | `input` + `reference_output`；质量按官方标准 | 模型优化训练 |

### 6.4 对比与回归门禁

平台的评估任务对比采用基线组/对照组思路，可查看综合得分、雷达图、各评估器得分、模型调用耗时和 Tokens，并下钻到单条数据的输出/得分差异。

对比约束：
- 仅支持**离线评估任务**对比
- 任务状态必须为成功或部分成功
- 对比任务必须基于**同一评测集**
- 单次最多对比 **5 个**评估任务

**推荐发布门禁**：
1. 核心质量指标达到业务目标
2. 相比基线，目标指标有提升或保持
3. 安全、拒答、工具参数和其他关键维度无显著退化
4. 耗时与 Token 成本处于预算
5. 所有高风险 BadCase 经人工复核

> 阈值由业务自行定义；官方文档未给出通用固定阈值。

## 7. 优化验收清单

- [ ] 每项优化都有可检验的假设和量化指标，不是"感觉更好"
- [ ] **先判断根因层次**：描述层（工具优化）/ 文档层（Skill 优化）/ 模型层（模型优化）/ 说不清（先轨迹分析）
- [ ] 平台任务所需的 **IAM 信任委托**已创建并授权（云服务填"智果 Agent 优化"）
- [ ] 目标智能体在时间范围内**已产生足量 Trace**（否则分析覆盖度与准确性受影响）
- [ ] 用**新的会话 ID** 做灰度/对照验证，避免会话存储与版本不一致导致超时
- [ ] 基线任务、评测集版本、评估器版本和关键参数均已固定
- [ ] BadCase 保留 `trace_id` 并按 Prompt/Model/RAG/Tool/Skill/Flow/数据/评估器归类
- [ ] 一次只改一个主要变量，改动可回滚
- [ ] 模型优化前确认**优化对象满足配置要求**（无工作流/子工作流、插件 ≤5、MCP ≤5、无用户交互节点在路径上、被优化节点不在循环中）
- [ ] 模型优化已准备**高质量数据集**，并选择合适奖惩机制
- [ ] 生成式奖励已撰写完整评分标准，且已确认裁判模型费用承担方
- [ ] 自定义奖励已创建并初始化代码解释器（含依赖与自定义 Python 文件）
- [ ] 对比评估使用同一评测集，并检查关键非目标指标是否退化
- [ ] 高分样本和低分 BadCase 分别沉淀，评测集发布新版本
- [ ] 新版本发布后继续在线观测，异常时可追溯与回滚
